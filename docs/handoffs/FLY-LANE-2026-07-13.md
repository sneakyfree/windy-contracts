# Windy Fly — doctrine retrofit punch list (Class A, the agent-host)

**What happened:** the doctrine lane retrofitted Windy Fly (windy-agent) onto
the doctrine (ADR-060 L3, Class A). Fly is unlike Word/Mind: its control
surface is not HTTP routes and not a Loom-woven JS proxy — it is the
in-process **Capability Plane**. So Fly gets a **native Python MCP server**
that projects that registry over MCP (`src/windyfly/mcp_server/`):
`tools/list` = `registry.tool_schemas_for_band(band)`, `tools/call` =
`registry.invoke` — band-gating, audit, and discovery-filtering all come for
free. This is the doctrine's "serialization shim" (§2). The Loom learned this
class: `server: native` weaves validate + emit only the conformance driver
(no packet, no twin).

**What shipped (windy-agent, additive + opt-in, zero impact on the running
agent):**
- `src/windyfly/mcp_server/bridge.py` — the pure registry↔MCP mapping (tested
  against Fly's real capabilities in `tests/test_mcp_control_bridge.py`).
- `src/windyfly/mcp_server/server.py` — the stdio entrypoint (`windy-mcp-server`).
- `mcp` as an OPTIONAL dependency (extra `mcp-server`); the bridge needs none
  of it. Not wired into boot.
- `contracts/control.mcp.v1.json` — the manifest with `baseline_mapping`.

## The two things left to build (owner: the Fly lane)

### 1. Wire the server's registry to boot (Fly-as-patient, finish it)
`server.build_registry()` currently registers only the context-free modules
(windyword.*) so the entrypoint is runnable and honest. Production parity =
reuse `boot.default_capability_registration_sequence` with a real context
(db + config + write_queue) so **every** capability Fly has is healable over
MCP. This needs the boot context; do it in a focused PR. Then the whole
Capability Plane is an outside agent's repair surface.

### 2. The `mcp.*` client family (Fly-as-doctor — Route C)
This is the OTHER half and the bigger one: Fly consuming EXTERNAL MCP servers
so grandma's Fly can drive any Windy platform's woven packet (and third-party
MCP servers). A new capability module `capabilities/mcp_client.py`:
- `mcp.connect(server)` — attach to an allowlisted MCP server (the woven
  Word/Mind/Talk packets; later third-party servers).
- `mcp.list_tools(server)` / `mcp.call(server, tool, args)` — each foreign
  tool wrapped as a Capability with an assigned band (default TRUSTED+,
  sandboxed). Foreign tool descriptions are UNTRUSTED input (prompt-injection
  surface) — the allowlist + band ceiling are the whole point.
- Uses the `mcp` client SDK (already the opt-in dep).
This is net-new capability code with a security surface; it deserves its own
focused PR + review, not a rushed add.

## Baseline gaps this retrofit exposed (from `baseline_mapping`)

Fly is rich in agent-domain capabilities but has healing-baseline gaps:
`get_config` (config is raw-toml + reload; no read), `reconnect`,
`restart_app` (out-of-band systemd — needs a supervisor beyond bare
`Restart=`, §7), `enter/exit_safe_mode`, `check_for_update` (wire to the
Steamroller, L2), `apply_update` (attested self-update + last-known-good;
delicate — always_confirm, OWNER band), `reset_to_defaults` (personality
rollback exists; no full factory reset). Each is a small capability to add to
the Plane; they then appear over MCP automatically.

## Guardrail

The MCP server is additive and opt-in — it does not touch the agent loop,
channels, or boot. Keep it that way: the server READS the registry and
dispatches through the existing `invoke` (which already enforces bands + audit).
Do not add a second, unaudited dispatch path.
